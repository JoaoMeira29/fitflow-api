Roadmap

An AI workout and diet plan generator

A user fills in a profile. FitFlow computes their calorie and macro targets in code, asks an LLM to build a weekly workout plan and a daily meal plan from its own catalogs, validates every plan, and stores it.

Design rules

Six rules the whole project follows. They are what makes the generated plans trustworthy.

1. The LLM chooses, the code calculates

Calorie and macro targets come from plain Python functions (Mifflin-St Jeor plus an activity multiplier) with unit tests. The model never does arithmetic.

2. Catalog only

The model may only use exercises and foods from FitFlow's own seeded catalogs, referenced by ID. It cannot invent items.

3. Structured output

Model output is parsed into Pydantic models. Anything that does not match the schema is rejected.

4. Validate every plan in code

IDs exist, exercises match the user's equipment, no allergens or restricted foods, calories within 5% of target, protein at or above target. The code may rescale portions; otherwise the errors go back to the model, for at most 2 retries.

5. One LLM wrapper

Every model call goes through app/core/llm.py, with a timeout, retries, and logging of latency and token usage. It is provider-agnostic.

6. Safety

A configurable minimum calorie floor, a cap on weekly weight change, no users under 18, and a "not medical advice" notice in every plan.

What each technology does

The role of each piece and where it lives in the code.

FastAPI

app/main.py, app/api/

Defines the routes, injects dependencies (database session, current user, LLM client) and generates the OpenAPI spec.

Pydantic

app/schemas/

Validates request bodies, shapes responses, and parses the LLM's structured output.

pydantic-settings

app/core/config.py

Reads and validates environment variables from .env. The app refuses to start if one is missing.

PostgreSQL

docker-compose.yml

Stores users, profiles, the two catalogs, generated plans and progress logs.

SQLAlchemy 2.0 + asyncpg

app/core/database.py, app/models/

Defines tables as Python classes and runs queries asynchronously. Each request gets its own session.

Alembic

alembic/

Generates and applies migrations, so the database schema is versioned in Git.

PyJWT + Argon2

app/core/security.py, app/api/auth.py

Argon2 hashes passwords; PyJWT signs and validates access tokens.

Targets calculator

app/core/targets.py

Pure functions that turn a profile into calorie and macro targets, with the safety limits applied.

LLM wrapper

app/core/llm.py

The single entry point for model calls. It talks to a local model served by Ollama (qwen2.5:7b by default) or to hosted Claude through the Anthropic SDK; the provider and model are settings.

Pytest + HTTPX

tests/, tests/evals/

Regular tests run against a test database with the LLM mocked. Evals call the real model under a separate marker.

Docker Compose

docker-compose.yml

Starts PostgreSQL locally with one command.

GitHub Actions

.github/workflows/

Runs migrations and the regular test suite on every push.

Data model

Plan items are real rows that point at the catalogs, so the database itself rejects an exercise or food that does not exist. Each plan keeps a snapshot of the profile that produced it.

Development phases

Each phase ends with a deliverable that works on its own, and includes its own tests.

1

Foundation and auth

Done
  • Project folder structure
  • FastAPI app with / and /health
  • app/core/config.py with pydantic-settings
  • db service (PostgreSQL 16) in docker-compose.yml
  • app/core/database.py with the async engine and one session per request
  • Alembic set up for async, reading the database URL from the app settings
  • users model and migration
  • app/core/security.py: Argon2 password hashing, JWT creation and validation
  • Password policy: 12 to 40 characters, and common passwords rejected from a bundled blocklist
  • POST /auth/register
  • POST /auth/login
  • GET /auth/me and the reusable get_current_user dependency
  • Tests for health, security and the auth flow, against a separate test database
Deliverable: a user can sign up, log in and call a protected route.
2

User profile

Done
  • profiles model and migration, one profile per user
  • Profile schemas with validated ranges and fixed choices (goal, sex, activity level, equipment, allergies, dietary restrictions)
  • PUT /profile to create or update the profile
  • GET /profile
  • Reject users under 18, based on birth date
  • Tests
Deliverable: a logged-in user can save the profile every later phase depends on.
3

Catalogs and targets calculator

Done
  • exercises model, migration and seed script (98 exercises, each listing the equipment it needs)
  • foods model, migration and seed script (197 foods, per 100 g, with allergens and diet tags)
  • GET /exercises and GET /foods with filters
  • app/core/targets.py: Mifflin-St Jeor, activity multiplier, goal adjustment and macro split, as pure functions
  • Safety limits: configurable calorie floor and cap on weekly weight change
  • GET /profile/targets returns the user's computed targets
  • Unit tests for the calculator
Deliverable: both catalogs are queryable and every profile has calorie and macro targets, with no LLM involved.
4

LLM wrapper and workout plans

Done
  • Choose the LLM provider and model: Ollama with qwen2.5:7b
  • app/core/llm.py: timeout, retries, logging of latency and token usage
  • Pydantic schema for the model's workout plan output
  • Validation: exercise IDs exist, equipment matches the profile, day count matches training days
  • Generate, validate and retry loop (at most 2 retries)
  • Workout plan tables and migration
  • POST /plans/workout, GET /plans/workout and GET /plans/workout/{id}
  • "Not medical advice" notice in plan responses
  • Tests with the LLM mocked
Deliverable: a user gets a stored weekly workout plan that only uses catalog exercises they have the equipment for.
5

Diet plans

Done
  • Pydantic schema for the model's diet plan output (food IDs and grams)
  • Validation: food IDs exist, no allergens or restricted foods, calories within 5% of target, protein at or above target
  • Portion rescaling in code: each meal is scaled to its share of the calorie target, then calories are moved towards its high-protein foods if protein is short
  • Optional calorie target chosen by the user, checked against the safety limits
  • Second provider, hosted Claude through the Anthropic SDK, and a calculate_nutrition tool the model can call on either provider
  • Diet plan tables and migration
  • POST /plans/diet, GET /plans/diet and GET /plans/diet/{id}
  • Tests with the LLM mocked
Deliverable: a user gets a stored daily meal plan that meets their targets and respects their allergies and restrictions.
6

Evals

Done
  • 30 varied test profiles in tests/evals/
  • Separate evals pytest marker, excluded from the regular test run
  • Report the pass rate for each validation rule
  • Record the results in the README
Deliverable: measured evidence of how often the real model produces a valid plan, per rule.
7

Progress and regeneration

Done
  • weight_logs and workout_logs models and migration
  • POST /progress/weight, POST /progress/workouts and GET /progress
  • Regeneration: the newest weight log updates the profile, so targets are recalculated from it, and a summary of the last 28 days of logs is included in the prompt
  • Tests
Deliverable: plans adapt to what the user actually did.
8

CI, deployment and docs

Done
  • GitHub Actions: PostgreSQL service, migrations, a model-versus-migration check, the regular tests and an image build on every push and PR
  • Dockerfile, and migration and API services in docker-compose.yml
  • Kubernetes manifests in k8s/
  • Final README and roadmap, including the eval results
Deliverable: a green pipeline, a containerised API and documentation that matches the product.
