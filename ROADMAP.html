Visão geral

A API é dona de tudo: valida os dados, autentica os utilizadores com JWT emitidos por ela própria e guarda a informação num PostgreSQL acedido via SQLAlchemy. O esquema da base de dados evolui através de migrações Alembic versionadas no repositório.

Papel de cada tecnologia

O que cada peça faz e onde vive no código.

FastAPI

app/main.py, app/api/

Define as rotas, injeta dependências (ex.: utilizador autenticado) e gera a especificação OpenAPI.

Uvicorn

Arranque / Dockerfile

Servidor ASGI que executa a aplicação.

Pydantic

app/schemas/

Valida os dados de entrada e formata as respostas.

pydantic-settings

app/core/config.py

Lê e valida as variáveis de ambiente do ficheiro .env.

PostgreSQL

docker-compose.yml, k8s/

Guarda utilizadores, exercícios, treinos e histórico.

SQLAlchemy 2.0 + asyncpg

app/core/database.py, app/models/

Define as tabelas como classes Python e executa as consultas de forma assíncrona. Cada pedido recebe a sua própria sessão.

Alembic

alembic/

Gera e aplica migrações, para que o esquema da base de dados fique versionado no Git.

PyJWT + Argon2

app/core/security.py, app/api/auth.py

Argon2 guarda as passwords em hash; PyJWT assina e valida os tokens de acesso.

Pytest + HTTPX

tests/

Testa os endpoints contra uma base de dados PostgreSQL de teste, sem levantar um servidor real.

Docker / Compose

Dockerfile, docker-compose.yml

Sobe a API e o PostgreSQL juntos com um só comando, sem precisar de internet.

Kubernetes

k8s/

Deploy, escalabilidade e health checks em produção.

Ciclo de um pedido

Exemplo: um utilizador autenticado cria um treino.

sequenceDiagram
    autonumber
    participant C as Cliente
    participant R as Rota FastAPI (workouts.py)
    participant D as get_current_user
    participant P as Pydantic
    participant DB as PostgreSQL
    C->>R: POST /workouts (Bearer token)
    R->>D: Resolver utilizador
    D->>D: Verificar assinatura e validade do JWT (PyJWT)
    D->>DB: SELECT utilizador pelo id do token
    DB-->>D: Utilizador encontrado
    R->>P: Validar corpo (WorkoutCreate)
    P-->>R: Dados válidos ou erro 422
    R->>DB: INSERT em workouts (user_id = id)
    DB-->>R: Registo criado
    R->>P: Serializar resposta (WorkoutRead)
    R-->>C: 201 Created + JSON
PassoErroCódigo
Token em falta ou inválidoNão autenticado401
Corpo inválidoErro de validação (Pydantic)422
Recurso de outro utilizadorA consulta filtra por user_id, por isso não é encontrado404

Modelo de dados

Em users a password nunca é guardada em texto, apenas o hash Argon2. exercises é um catálogo partilhado preenchido pelo app/seed.py. workouts pertence a um utilizador: todas as consultas filtram por user_id, para que cada utilizador só leia e escreva os seus próprios registos.

Fases de desenvolvimento

Cada fase termina com um entregável que funciona por si só.

1

Fundação

Em progresso
  • Estrutura de pastas do projeto
  • Aplicação FastAPI com / e /health
  • app/core/config.py com pydantic-settings (lê DATABASE_URL, JWT_SECRET e ACCESS_TOKEN_EXPIRE_MINUTES)
  • Serviço db (PostgreSQL 16) no docker-compose.yml
  • app/core/database.py com o engine async e uma dependência que abre e fecha uma sessão por pedido
  • Alembic inicializado e ligado aos modelos de app/models/
  • Primeiro teste: tests/test_health.py
Entregável: a API arranca, lê a configuração, liga-se ao PostgreSQL e corre migrações.
2

Autenticação

Planeado
  • Modelo e migração da tabela users
  • app/core/security.py: hash e verificação de passwords (Argon2), criação e validação de JWT
  • POST /auth/register para criar conta
  • POST /auth/login devolve access_token e refresh_token
  • POST /auth/refresh para renovar a sessão
  • GET /auth/me com os dados do utilizador autenticado
  • Dependência get_current_user reutilizável nas rotas protegidas
Entregável: um utilizador consegue registar-se, fazer login e aceder a rotas protegidas.
3

Catálogo de exercícios

Planeado
  • Modelo Exercise e migração Alembic da tabela exercises
  • Schema ExerciseRead em app/schemas/exercise.py
  • GET /exercises com filtros por muscle_group e equipment
  • GET /exercises/{id} com o detalhe de um exercício
  • app/seed.py para povoar o catálogo inicial
Entregável: catálogo de exercícios consultável pela API.
4

Gestão de treinos

Planeado
  • Modelos e migração das tabelas workouts e workout_exercises
  • Schemas WorkoutCreate, WorkoutUpdate e WorkoutRead
  • POST /workouts cria um treino com exercícios, séries, repetições e carga
  • GET /workouts lista os treinos do utilizador (paginado)
  • GET /workouts/{id} com o detalhe
  • PATCH /workouts/{id} para editar
  • DELETE /workouts/{id} para apagar
Entregável: CRUD completo de treinos. Todas as consultas filtram por user_id, e um teste garante que um utilizador não vê os treinos de outro.
5

Progresso

Planeado
  • GET /progress/summary com total de treinos, volume semanal e exercícios mais feitos
  • GET /progress/exercises/{id} com a evolução da carga ao longo do tempo
Entregável: o utilizador consegue ver a sua evolução.
6

Qualidade

Planeado
  • Testes de cada router com Pytest + HTTPX
  • Base de dados PostgreSQL de teste, limpa entre testes
  • CI (GitHub Actions) com um serviço PostgreSQL, a correr migrações e testes em cada push e PR
  • Tratamento de erros uniforme (um único formato JSON para erros)
Entregável: pipeline verde e cobertura dos fluxos principais.
7

Containerização e deploy

Planeado
  • Dockerfile com imagem python:3.11-slim e arranque com Uvicorn
  • docker-compose.yml completo: API + PostgreSQL com volume persistente
  • Migrações aplicadas automaticamente no arranque do container
  • k8s/deployment.yaml com réplicas, Secret para DATABASE_URL e JWT_SECRET e probes em /health
  • k8s/service.yaml para expor a API no cluster
  • PostgreSQL em produção: base de dados gerida (Neon, RDS) ou StatefulSet no cluster
Entregável: a API corre em Docker e é publicável num cluster Kubernetes.
