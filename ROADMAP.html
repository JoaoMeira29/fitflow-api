Overview

The API owns everything: it validates data, authenticates users with JWTs it issues itself, and stores data in PostgreSQL through SQLAlchemy. The database schema evolves through Alembic migrations versioned in the repository.

What each technology does

The role of each piece and where it lives in the code.

FastAPI

app/main.py, app/api/

Defines the routes, injects dependencies (e.g. the authenticated user) and generates the OpenAPI spec.

Uvicorn

Startup / Dockerfile

ASGI server that runs the application.

Pydantic

app/schemas/

Validates incoming data and shapes the responses.

pydantic-settings

app/core/config.py

Reads and validates the environment variables from the .env file.

PostgreSQL

docker-compose.yml, k8s/

Stores users, exercises, workouts and history.

SQLAlchemy 2.0 + asyncpg

app/core/database.py, app/models/

Defines tables as Python classes and runs queries asynchronously. Each request gets its own session.

Alembic

alembic/

Generates and applies migrations, so the database schema is versioned in Git.

PyJWT + Argon2

app/core/security.py, app/api/auth.py

Argon2 hashes passwords; PyJWT signs and validates access tokens.

Pytest + HTTPX

tests/

Tests the endpoints against a test PostgreSQL database, without starting a real server.

Docker / Compose

Dockerfile, docker-compose.yml

Starts the API and PostgreSQL together with one command, no internet required.

Kubernetes

k8s/

Deployment, scaling and health checks in production.

Request lifecycle

Example: an authenticated user creates a workout.

sequenceDiagram
    autonumber
    participant C as Client
    participant R as FastAPI route (workouts.py)
    participant D as get_current_user
    participant P as Pydantic
    participant DB as PostgreSQL
    C->>R: POST /workouts (Bearer token)
    R->>D: Resolve user
    D->>D: Check JWT signature and expiry (PyJWT)
    D->>DB: SELECT user by token id
    DB-->>D: User found
    R->>P: Validate body (WorkoutCreate)
    P-->>R: Valid data or 422 error
    R->>DB: INSERT into workouts (user_id = id)
    DB-->>R: Row created
    R->>P: Serialize response (WorkoutRead)
    R-->>C: 201 Created + JSON

Data model

In users the password is never stored as plain text, only its Argon2 hash. exercises is a shared catalog filled by app/seed.py. workouts belong to a user: every query filters by user_id, so each user only reads and writes their own records.

erDiagram
    USERS ||--o{ WORKOUTS : creates
    WORKOUTS ||--|{ WORKOUT_EXERCISES : contains
    EXERCISES ||--o{ WORKOUT_EXERCISES : "used in"
    USERS {
        uuid id PK
        string email UK
        string password_hash
        timestamp created_at
    }
    EXERCISES {
        uuid id PK
        string name
        string muscle_group
        string equipment
        text description
    }
    WORKOUTS {
        uuid id PK
        uuid user_id FK
        string name
        date performed_at
        text notes
    }
    WORKOUT_EXERCISES {
        uuid id PK
        uuid workout_id FK
        uuid exercise_id FK
        int sets
        int reps
        float weight_kg
    }

Development phases

Each phase ends with a deliverable that works on its own.

1

Foundation

In progress
  • Project folder structure
  • FastAPI app with / and /health
  • app/core/config.py with pydantic-settings (reads DATABASE_URL, JWT_SECRET and ACCESS_TOKEN_EXPIRE_MINUTES)
  • db service (PostgreSQL 16) in docker-compose.yml
  • app/core/database.py with the async engine and a dependency that opens and closes one session per request
  • Alembic initialized and wired to the models in app/models/
  • First test: tests/test_health.py
Deliverable: the API starts, reads its settings, connects to PostgreSQL and runs migrations.
2

Authentication

Planned
  • users model and migration
  • app/core/security.py: password hashing and verification (Argon2), JWT creation and validation
  • POST /auth/register to create an account
  • POST /auth/login returns access_token and refresh_token
  • POST /auth/refresh to renew the session
  • GET /auth/me returns the authenticated user
  • Reusable get_current_user dependency for protected routes
Deliverable: a user can sign up, log in and access protected routes.
3

Exercise catalog

Planned
  • Exercise model and Alembic migration for the exercises table
  • ExerciseRead schema in app/schemas/exercise.py
  • GET /exercises with muscle_group and equipment filters
  • GET /exercises/{id} returns a single exercise
  • app/seed.py to fill the initial catalog
Deliverable: an exercise catalog you can query through the API.
4

Workout management

Planned
  • Models and migration for the workouts and workout_exercises tables
  • WorkoutCreate, WorkoutUpdate and WorkoutRead schemas
  • POST /workouts creates a workout with exercises, sets, reps and weight
  • GET /workouts lists the user's workouts (paginated)
  • GET /workouts/{id} returns a single workout
  • PATCH /workouts/{id} to edit
  • DELETE /workouts/{id} to delete
Deliverable: full workout CRUD. Every query filters by user_id, and a test ensures a user cannot see another user's workouts.
5

Progress

Planned
  • GET /progress/summary with total workouts, weekly volume and most-used exercises
  • GET /progress/exercises/{id} with weight progression over time
Deliverable: users can see their progress.
6

Quality

Planned
  • Tests for every router with Pytest + HTTPX
  • Test PostgreSQL database, cleaned between tests
  • CI (GitHub Actions) with a PostgreSQL service, running migrations and tests on every push and PR
  • Consistent error handling (a single JSON format for errors)
Deliverable: a green pipeline and coverage of the main flows.
7

Containers and deployment

Planned
  • Dockerfile based on python:3.11-slim, started with Uvicorn
  • Complete docker-compose.yml: API + PostgreSQL with a persistent volume
  • Migrations applied automatically when the container starts
  • k8s/deployment.yaml with replicas, a Secret for DATABASE_URL and JWT_SECRET, and probes on /health
  • k8s/service.yaml to expose the API inside the cluster
  • PostgreSQL in production: a managed database (Neon, RDS) or a StatefulSet in the cluster
Deliverable: the API runs in Docker and can be deployed to a Kubernetes cluster.
