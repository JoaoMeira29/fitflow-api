Visão geral

A API é uma camada fina entre o cliente e o Supabase: valida os dados, aplica as regras de negócio e devolve respostas consistentes. A autenticação e o armazenamento ficam a cargo do Supabase.

Papel de cada tecnologia

O que cada peça faz e onde vive no código.

FastAPI

app/main.py, app/api/

Define as rotas, injeta dependências (ex.: utilizador autenticado) e gera a especificação OpenAPI.

Uvicorn

Arranque / Dockerfile

Servidor ASGI que executa a aplicação.

Pydantic

app/schemas/

Valida os dados de entrada e formata as respostas.

pydantic-settings

app/core/config.py

Lê e valida as variáveis de ambiente do ficheiro .env.

Supabase Auth

app/api/auth.py

Registo, login e emissão de tokens JWT.

Supabase Postgres

app/core/supabase.py

Guarda exercícios, treinos e histórico. O RLS garante que cada utilizador só vê os seus dados.

Pytest + HTTPX

tests/

Testa os endpoints sem levantar um servidor real.

Docker / Compose

Dockerfile, docker-compose.yml

Ambiente reproduzível para desenvolvimento e produção.

Kubernetes

k8s/

Deploy, escalabilidade e health checks em produção.

Ciclo de um pedido

Exemplo: um utilizador autenticado cria um treino.

sequenceDiagram
    autonumber
    participant C as Cliente
    participant R as Rota FastAPI (workouts.py)
    participant D as get_current_user
    participant S as Supabase Auth
    participant P as Pydantic
    participant DB as PostgreSQL
    C->>R: POST /workouts (Bearer token)
    R->>D: Resolver utilizador
    D->>S: Validar token JWT
    S-->>D: Utilizador válido (id)
    R->>P: Validar corpo (WorkoutCreate)
    P-->>R: Dados válidos ou erro 422
    R->>DB: INSERT em workouts (user_id = id)
    DB-->>R: Registo criado
    R->>P: Serializar resposta (WorkoutRead)
    R-->>C: 201 Created + JSON
PassoErroCódigo
Token em falta ou inválidoNão autenticado401
Corpo inválidoErro de validação (Pydantic)422
Recurso de outro utilizadorBloqueado pelo RLS404

Modelo de dados

A tabela users é gerida pelo Supabase Auth, por isso a API não guarda passwords. exercises é um catálogo partilhado preenchido pelo app/seed.py. workouts e workout_exercises têm RLS: cada utilizador só lê e escreve os seus próprios registos.

erDiagram
    USERS ||--o{ WORKOUTS : cria
    WORKOUTS ||--|{ WORKOUT_EXERCISES : contem
    EXERCISES ||--o{ WORKOUT_EXERCISES : "usado em"
    USERS {
        uuid id PK
        string email
    }
    EXERCISES {
        uuid id PK
        string name
        string muscle_group
        string equipment
        text description
    }
    WORKOUTS {
        uuid id PK
        uuid user_id FK
        string name
        date performed_at
        text notes
    }
    WORKOUT_EXERCISES {
        uuid id PK
        uuid workout_id FK
        uuid exercise_id FK
        int sets
        int reps
        float weight_kg
    }

Fases de desenvolvimento

Cada fase termina com um entregável que funciona por si só.

1

Fundação

Em progresso
  • Estrutura de pastas do projeto
  • Aplicação FastAPI com / e /health
  • app/core/config.py com pydantic-settings (lê SUPABASE_URL e SUPABASE_KEY)
  • app/core/supabase.py com o cliente Supabase partilhado
  • Primeiro teste: tests/test_health.py
Entregável: a API arranca, lê a configuração e liga-se ao Supabase.
2

Autenticação

Planeado
  • POST /auth/register para criar conta
  • POST /auth/login devolve access_token e refresh_token
  • POST /auth/refresh para renovar a sessão
  • GET /auth/me com os dados do utilizador autenticado
  • Dependência get_current_user reutilizável nas rotas protegidas
Entregável: um utilizador consegue registar-se, fazer login e aceder a rotas protegidas.
3

Catálogo de exercícios

Planeado
  • Tabela exercises no Supabase
  • Schema ExerciseRead em app/schemas/exercise.py
  • GET /exercises com filtros por muscle_group e equipment
  • GET /exercises/{id} com o detalhe de um exercício
  • app/seed.py para povoar o catálogo inicial
Entregável: catálogo de exercícios consultável pela API.
4

Gestão de treinos

Planeado
  • Tabelas workouts e workout_exercises com políticas RLS
  • Schemas WorkoutCreate, WorkoutUpdate e WorkoutRead
  • POST /workouts cria um treino com exercícios, séries, repetições e carga
  • GET /workouts lista os treinos do utilizador (paginado)
  • GET /workouts/{id} com o detalhe
  • PATCH /workouts/{id} para editar
  • DELETE /workouts/{id} para apagar
Entregável: CRUD completo de treinos, isolado por utilizador.
5

Progresso

Planeado
  • GET /progress/summary com total de treinos, volume semanal e exercícios mais feitos
  • GET /progress/exercises/{id} com a evolução da carga ao longo do tempo
Entregável: o utilizador consegue ver a sua evolução.
6

Qualidade

Planeado
  • Testes de cada router com Pytest + HTTPX
  • Mocks do cliente Supabase para testes rápidos e isolados
  • CI (GitHub Actions) a correr os testes em cada push e PR
  • Tratamento de erros uniforme (um único formato JSON para erros)
Entregável: pipeline verde e cobertura dos fluxos principais.
7

Containerização e deploy

Planeado
  • Dockerfile com imagem python:3.11-slim e arranque com Uvicorn
  • docker-compose.yml para desenvolvimento local
  • k8s/deployment.yaml com réplicas, Secret para as credenciais e probes em /health
  • k8s/service.yaml para expor a API no cluster
Entregável: a API corre em Docker e é publicável num cluster Kubernetes.
